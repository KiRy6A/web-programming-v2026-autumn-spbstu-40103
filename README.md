# Лабораторные работы по веб-программированию

Этот репозиторий используется для сдачи лабораторных работ. Каждая работа
отправляется отдельным pull request и автоматически проверяется перед защитой.

Зелёный CI означает, что работа соответствует формальным требованиям и допущена
к защите. Окончательно работа принимается преподавателем после вопросов и live
coding. Принятая работа появляется в основной ветке после squash merge.

## 1. Что нужно установить

- Git;
- Node.js `24.19.0` — версия указана в `.nvmrc`;
- npm;
- редактор кода, например VS Code.

После клонирования или обновления fork перейдите в корень репозитория и один раз
установите локальные инструменты:

```bash
npm install
```

`node_modules` используется только локально и не должен попадать в Git.

## 2. Как называется каталог студента

Все работы одного студента находятся в каталоге:

```text
surname.name/
```

Требования:

- только lowercase Latin;
- сначала фамилия, затем точка и имя;
- пробелы, кириллица и `_` запрещены;
- внутри фамилии или имени разрешён дефис.

Правильно:

```text
ivanov.ivan
petrov-sidorov.alexey
```

Неправильно:

```text
Ivanov.Ivan
ivanov
иванов.иван
ivanov_ivan
```

## 3. Структура работ

Каждая лабораторная находится в отдельном подкаталоге:

```text
surname.name/
├── lab1/
├── lab2/
├── lab3/
├── lab4/
└── lab5/
```

Минимальные заготовки для всех лабораторных находятся в каталоге `templates/`.
Скопируйте заготовку нужной работы в свой каталог, например:

```bash
mkdir -p surname.name
cp -R templates/lab2 surname.name/lab2
```

Заготовка содержит только минимально обязательные файлы. Перед сдачей замените
все указанные в ней заглушки реализацией своего варианта.

Один pull request должен изменять только одну лабораторную одного студента.
Например, PR для второй лабораторной `ivanov.ivan` может содержать изменения
только внутри:

```text
ivanov.ivan/lab2/
```

Нельзя добавлять в студенческий PR:

- файлы другого студента;
- несколько лабораторных одновременно;
- изменения `.github`, CI или корневых конфигов;
- lock-файлы внутри лабораторной;
- `package.json` внутри lab1–lab4 или вне корня lab5;
- `node_modules` и `dist`;
- symlink, submodule и executable-файлы.

Изображения помещайте в подкаталог `assets/` своей лабораторной:

```text
surname.name/lab5/assets/cover.webp
```

## 4. Обязательные файлы

Дополнительные компоненты и модули разрешены внутри текущей лабораторной.

| Работа | Обязательные файлы                                                                                    |
| ------ | ----------------------------------------------------------------------------------------------------- |
| lab1   | `README.md`, `index.html`, `styles.css`                                                               |
| lab2   | `README.md` и ровно один из `solution.js`, `solution.ts`                                              |
| lab3   | `README.md` и ровно один из `solution.js`, `solution.ts`                                              |
| lab4   | `README.md`, `index.html`, `styles.css`, ровно один `main.js/main.ts`, ровно один `model.js/model.ts` |
| lab5   | `README.md`, React `package.json`, HTML, CSS и один JS/JSX/TS/TSX entry                               |

Файл `submission.json` не используется. Номер варианта берётся из названия PR.

## 5. README каждой лабораторной

В каждой работе должен находиться отдельный `README.md`. Первая строка содержит
номер лабораторной, а обязательные разделы идут ровно в указанном порядке и не
могут быть пустыми.

Шаблон для lab2:

```markdown
# Лабораторная работа 2

## Задание

Опишите свой вариант и требования задания.

## Реализация

Опишите структуру решения, основные функции, классы и принятые решения.

## Запуск

Опишите, как открыть страницу или запустить решение локально.
```

Для другой работы замените номер в первой строке.

## 6. Как называется pull request

Название PR должно в точности соответствовать формату:

```text
[TASK-N] variant_K surname.name
```

Где:

- `N` — номер лабораторной от 1 до 5;
- `K` — выданный преподавателем вариант от 1 до 40;
- `surname.name` — название вашего каталога.

Пример сдачи второй лабораторной, варианта 2:

```text
[TASK-2] variant_2 testov.oleg
```

Недопустимы дополнительные слова, другой регистр, лишние пробелы или другое
расположение частей названия.

Неправильно:

```text
Lab 2 testov.oleg
[TASK-2] testov.oleg variant_2
[TASK-2] variant-2 testov.oleg
[TASK-2] variant_2 Testov.Oleg
```

После первой принятой работы GitHub-пользователь и вариант привязываются к
`surname.name`. В следующих PR нельзя использовать другой вариант или открыть
работу от имени другого GitHub-пользователя.

## 7. Требования к lab1

Lab1 состоит из HTML-страницы и CSS.

Минимальная структура:

```text
surname.name/lab1/
├── README.md
├── index.html
└── styles.css
```

Требования:

- валидный `<!doctype html>`;
- непустой `<title>`;
- подключённый `styles.css`;
- семантическая или интерактивная разметка;
- отсутствие inline styles;
- отсутствие ошибок загрузки ресурсов и браузерной консоли;
- отсутствие горизонтального overflow;
- выполнение DOM/CSS-контракта своего варианта;
- работа hover, focus и responsive-состояний, если они есть в задании.

CI проверяет не только наличие текста, но и DOM, computed styles, размеры,
расположение элементов и состояния интерфейса.

## 8. Требования к lab2 и lab3

Решение находится в `solution.js` или `solution.ts` и является ES module.

Минимальная структура:

```text
surname.name/lab2/
├── README.md
└── solution.js
```

Функция должна экспортироваться под именем, назначенным вашему варианту:

```js
export function toRoman(value) {
  // Реализация.
}
```

Также допустим отдельный именованный export:

```js
function toRoman(value) {
  // Реализация.
}

export {toRoman};
```

Не подходят:

```js
export default function toRoman() {}

function toRoman() {}
```

Общие требования:

- имя export соответствует варианту;
- функция возвращает результат, а не только выводит его в консоль;
- входные массивы не изменяются, если задание явно не требует обратного;
- синхронная задача не возвращает Promise;
- решение работает на граничных случаях, а не только на примерах;
- запрещён хардкод только под известные тестовые значения.

Открытая таблица функций и уточнений для lab2/lab3 находится в
[контрактах задач](https://github.com/web-programming-contest/web-programming-ci-utils/blob/master/docs/TASK_CONTRACTS.md).

## 9. Требования к lab4

Lab4 разделяет модель и пользовательский интерфейс.

```text
surname.name/lab4/
├── README.md
├── index.html
├── styles.css
├── main.js
├── model.js
└── components/       # Опционально
```

Каждую точку входа можно написать на JavaScript или TypeScript: например,
`main.ts` вместе с `model.ts` либо `main.js` вместе с `model.js`. Нельзя
одновременно оставлять `.js` и `.ts` версию одной и той же точки входа.

### Модель

`model.js/model.ts` должен именованно экспортировать:

- класс своего варианта;
- функции работы с коллекцией, указанные в задании.

Пример:

```js
export class Library {
  // Конструктор и методы.
}

export function groupBooksByGenre(libraries) {
  // Реализация.
}
```

Проверяются constructor, поля/getter, методы добавления и удаления, результаты
функций коллекций и отсутствие изменения входного массива.

### Интерфейс

Обязательный публичный DOM-контракт:

| Элемент                         | Селектор                          |
| ------------------------------- | --------------------------------- |
| Список сущностей                | `[data-testid="entity-list"]`     |
| Форма добавления                | `form[data-testid="entity-form"]` |
| Карточка сущности               | `[data-testid="entity-card"]`     |
| Кнопка удаления внутри карточки | `[data-testid="delete-entity"]`   |

Поля формы должны иметь атрибут `name`, соответствующий полям вашего варианта.

Дополнительные требования:

- добавление и удаление выполняются асинхронно через `setTimeout`;
- DOM обновляется без перезагрузки страницы;
- состояние сохраняется в `localStorage`;
- после reload данные восстанавливаются;
- удаление обновляет и DOM, и `localStorage`.

Названия классов, функций и полей формы опубликованы в
[контрактах lab4](https://github.com/web-programming-contest/web-programming-ci-utils/blob/master/docs/TASK_CONTRACTS.md#lab4).

## 10. Требования к lab5

Lab5 — интерактивное React-приложение. Его можно написать на JavaScript или
TypeScript и собирать локально с помощью Vite либо Webpack.

```text
surname.name/lab5/
├── README.md
├── package.json
├── index.html
├── src/
│   ├── main.jsx       # Либо main.tsx/index.jsx/index.tsx
│   ├── styles.css
│   └── components/    # Опционально
└── assets/           # Опционально
```

Также поддерживается Webpack-структура с `public/index.html`. HTML должен быть
ровно один: `index.html` либо `public/index.html`. Entry можно подключить через
локальный `script src` или разместить в `main.*`, `src/main.*`, `src/index.*`,
где расширение — `.js`, `.jsx`, `.ts` или `.tsx`.

`package.json` должен объявлять `react`, `react-dom`, `vite` или `webpack`, а
также script `build`. CI проверяет manifest, но не устанавливает студенческие
зависимости и не выполняет scripts: приложение безопасно пересобирается
закреплённым toolchain grader.

Корневой элемент приложения должен иметь:

```html
<main data-testid="app"></main>
```

Для каждого варианта дополнительно определены публичные `data-testid` и
пользовательские сценарии. CI может проверять:

- click и ввод в поля;
- select и клавиатуру;
- drag-and-drop;
- изменение текста, значения, атрибута и количества элементов;
- изменение визуального состояния;
- сохранение в `localStorage`;
- восстановление после reload.

Приложение проверяется без доступа к интернету. Не загружайте данные,
JavaScript, CSS или изображения из внешнего API/CDN. Все необходимые ресурсы и
начальные данные должны находиться внутри лабораторной.

Для локального запуска сначала установите зависимости внутри lab5, затем
используйте script выбранного сборщика:

```bash
cd surname.name/lab5
npm install
npm run dev
```

Публичные селекторы и сценарии находятся в
[контрактах lab5](https://github.com/web-programming-contest/web-programming-ci-utils/blob/master/docker-grader/contracts/lab5/scenarios.json).

## 11. Локальные проверки перед push

Все команды запускаются из корня репозитория курса, не из каталога лабораторной.

В примерах замените `surname.name/labN` своим каталогом.

### Автоматически исправить форматирование

```bash
npm run format -- surname.name/labN
```

Команда форматирует JavaScript, TypeScript, HTML, CSS, JSON и Markdown, включая
`README.md`. После неё обязательно посмотрите `git diff`.

### Только проверить форматирование

```bash
npm run format:check -- surname.name/labN
```

### Проверить JavaScript и TypeScript

```bash
npm run lint:js -- surname.name/labN
```

Warnings считаются ошибками.

### Проверить CSS

```bash
npm run lint:css -- "surname.name/labN/**/*.css"
```

Основные правила:

- классы называются в kebab-case;
- ID-селекторы запрещены;
- `!important` запрещён;
- используются современные CSS-нотации.

### Проверить HTML

```bash
npm run lint:html -- "surname.name/labN/**/*.html"
```

Проверяются структура, обязательные атрибуты, семантика, doctype и отсутствие
inline styles.

### Проверить TypeScript в strict mode

Если работа написана на TypeScript:

```bash
npx tsc \
  --noEmit \
  --strict \
  --jsx react-jsx \
  --target ES2022 \
  --module ESNext \
  --moduleResolution Bundler \
  --lib ES2022,DOM,DOM.Iterable \
  --skipLibCheck \
  surname.name/lab2/solution.ts
```

Для UI-работы вместо `solution.ts` укажите точки входа, например
`surname.name/lab4/main.ts surname.name/lab4/model.ts` или
`surname.name/lab5/src/main.tsx`. Импортированные ими TypeScript-компоненты
будут проверены автоматически.

### Рекомендуемый порядок

```bash
npm run format -- surname.name/labN
npm run format:check -- surname.name/labN
npm run lint:js -- surname.name/labN
```

Для UI-лабораторной дополнительно:

```bash
npm run lint:css -- "surname.name/labN/**/*.css"
npm run lint:html -- "surname.name/labN/**/*.html"
```

Локальные команды проверяют форматирование и code style. Функциональные и
браузерные тесты полностью запускаются в GitHub CI после создания PR.

## 12. Порядок сдачи

1. Получите вариант у преподавателя.
2. Обновите свою основную ветку из репозитория курса.
3. Создайте отдельную ветку для одной лабораторной.
4. Создайте каталог `surname.name/labN`.
5. Добавьте обязательные файлы и заполните README.
6. Запустите локальные проверки.
7. Проверьте `git status` и `git diff`.
8. Убедитесь, что изменена только одна лабораторная.
9. Создайте commit и отправьте ветку в свой fork.
10. Откройте PR в основную ветку репозитория курса.
11. Укажите точное название `[TASK-N] variant_K surname.name`.
12. Дождитесь CI и исправьте все ошибки.
13. После зелёного CI приходите на защиту.

После любого нового push старый CI run отменяется и запускается новый. Если вы
изменили название PR, проверка также запускается повторно.

## 13. Что проверяет CI

Сначала PR Gate проверяет:

- название PR;
- единственный изменённый каталог;
- обязательные файлы;
- README;
- вариант и задачу;
- GitHub-пользователя;
- запрещённые типы и размеры файлов.

Затем Docker grader выполняет применимые этапы:

| Этап                   | Назначение                           |
| ---------------------- | ------------------------------------ |
| Prettier               | Форматирование всех текстовых файлов |
| ESLint                 | JavaScript/TypeScript и code style   |
| Stylelint              | CSS                                  |
| HTML Validate          | HTML и семантика                     |
| TypeScript strict mode | Проверка типов без генерации файлов  |
| Functional validation  | Функции lab2/lab3                    |
| Model validation       | Класс и функции lab4                 |
| Browser validation     | DOM/CSS/UI-сценарии lab1/lab4/lab5   |

Неприменимые этапы отображаются как `Skipped`.

## 14. Где смотреть ошибки

В PR откройте `Checks`, затем конкретный упавший job.

На странице workflow run в `Summary` находится таблица:

| Этап     | Статус        | Время | Причина             |
| -------- | ------------- | ----- | ------------------- |
| Prettier | Passed/Failed | Время | Краткая диагностика |
| ESLint   | Passed/Failed | Время | Краткая диагностика |
| ...      | ...           | ...   | ...                 |

Ниже таблицы раскрывается полный stdout/stderr каждого упавшего этапа. Ошибки
также отображаются как annotations.

В artifact `grader-results-<PR number>` находятся:

- `summary.json`;
- `report.md`;
- Docker logs;
- browser HTML-report;
- screenshot;
- Playwright trace при browser failure.

## 15. Частые ошибки

### `File outside the only allowed directory`

В PR попал файл вне `surname.name/labN`. Удалите его из commit или создайте
отдельный PR.

### `PR title must exactly match`

Исправьте название по шаблону:

```text
[TASK-N] variant_K surname.name
```

### `Expected named ESM export`

Функция или класс не экспортированы либо имя не соответствует варианту.
Проверьте публичный контракт и используйте именованный `export`.

### Prettier показывает README или исходный код

Выполните:

```bash
npm run format -- surname.name/labN
```

Затем добавьте изменения в commit и отправьте новый push.

### ESLint/Stylelint показывает warnings

Warnings блокируют CI так же, как errors. Исправьте каждое сообщение и повторно
запустите локальный checker.

### Browser validation не находит элемент

Проверьте обязательный `data-testid`, видимость элемента и соответствие сценарию
своего варианта. Затем скачайте screenshot и trace из artifact.

### Action не запускается

Для первого PR из нового fork GitHub может ожидать ручного разрешения
преподавателя. Также убедитесь, что PR направлен в основную ветку курса.

## 16. Перед открытием PR

- [ ] Название PR соответствует `[TASK-N] variant_K surname.name`.
- [ ] Изменена только одна папка `surname.name/labN`.
- [ ] Все обязательные файлы присутствуют.
- [ ] README заполнен и соответствует шаблону.
- [ ] Вариант указан правильно.
- [ ] Именованные exports соответствуют заданию.
- [ ] Все необходимые `data-testid` добавлены.
- [ ] `npm run format:check` проходит.
- [ ] ESLint проходит без warnings.
- [ ] Для UI-работ проходят Stylelint и HTML Validate.
- [ ] В commit нет `node_modules`, lock-файлов и чужих работ.

После зелёного CI подготовьтесь объяснить решение и внести небольшое изменение
во время защиты.
